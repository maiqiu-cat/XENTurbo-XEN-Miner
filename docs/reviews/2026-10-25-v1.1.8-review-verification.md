## 1. 结论

1. 三个指定 RPC 现象均已用仓库测试写法及真实锁定版本 ethers 复现。确认超时、恢复中断、部分验证的应用自写安全提示在繁体界面仍有英文，P2-i1 属实，按本项目尺度定为 P2 合理。
2. 原报告多数源码引用正确，但包含一处明确错行及多处过度概括。不能将所有“子代理实测”数字视为本轮已复现，也不能将建议直接当作经过验证的修复方案。
3. 本轮 Ethereum 四个默认端点均接受 400 条 Multicall 的 128,064 字节原始 ABI 返回。Polygon 三个端点表现出 100,000 字节边界，当前 300 条限制应保留。
4. Tenderly 双链的 CORS 预检和真实浏览器三项 JSON-RPC 数组读取通过。本轮有限请求未触发限流；历史发布探针有 HTTP 429 / JSON-RPC -32005 证据，尚无本轮 HTTP 200 承载限流错误的证据。
5. PR #11 可以作为文档合并，不必等待运行时修复；这不表示缺陷已修复、全部场景无漏洞或批准生产发布。

**既有决定不变：无 hash 的损坏锁仍保留；P2-C 仍未证实，相关门禁不放宽。**

## 3. 三个 RPC 复现

源码依据：[provider 构造](https://github.com/maiqiu-cat/XENTurbo-XEN-Miner/blob/b2764b90a5af7b6a546a5745dbb48e7d55d4d7e8/src/core/rpc.ts#L120-L134)、[错误分类与外层重试](https://github.com/maiqiu-cat/XENTurbo-XEN-Miner/blob/b2764b90a5af7b6a546a5745dbb48e7d55d4d7e8/src/core/rpc.ts#L427-L510)。

| 场景 | 实测 | 判定 |
| --- | --- | --- |
| a. 第一节点 20 秒后响应，第二立即响应，quorum 1；读取 pending nonce | 第一节点约 16 ms 发出请求，第二约 2,523 ms 已返回正确值；最终约 **12,025 ms** 抛 TIMEOUT，没有返回第二节点的值 | 指定现象属实，结论限定为测试过的方法和配置。 |
| a. 成功/失败对照 | 健康首节点约 17 ms 成功；首节点立即 HTTP 503 时，调用立即失败，第二节点未救回 | 不是全部节点共同不可用造成的假阳性。 |
| b. Multicall HTTP 429，Retry-After: 1 | **48 个 eth_call POST**，约 **2,987 ms** 后 SERVER_ERROR | 12 次 ethers 传输尝试乘以 4 次应用尝试。外层等待 400+800+1600 ms；该头没有按秒等待。 |
| b. Retry-After: 30 对照 | 仍为 48 个 POST，约 **4,482 ms** | 内层间隔为几十毫秒，不是 30 秒，符合当前 ethers 实现的单位问题。 |
| c. eth_call 返回 JSON-RPC -32005 / Too Many Requests | CALL_EXCEPTION，info.error 保留原错误，isRetryableRpcError=false，仅 1 个 eth_call POST | 错误封装使外层不重试，属实。 |
| c. 错误类别对照 | 返回大小超限、节点执行超时、execution reverted、-32603 Internal error 也成为 CALL_EXCEPTION，当前均不重试 | 不能据此全部放行重试，必须区分暂态、确定性大小错误与合约回滚。 |

### 需要收窄的结论和建议

- “FallbackProvider 从不切换、任何方法永远不用后续节点”过强。以上 nonce 路径已证实；区块高度、Gas/费用、estimateGas 等存在其他聚合分支，初始化也可能访问多个端点。改成等优先级并非已验证的根治。
- 48 是本次单端点、快速 429、固定外层四次的结果，**不是所有 multicall 的全局上界**。多 runner、慢请求、无 Retry-After 等可能改变计数。
- `setThrottleParams({ maxAttempts: 2 })` 只是把本场景从 12×4 降为 2×4，即 8，**不会消除重试叠加**。要统一重试，应另外设计传输重试关闭、Retry-After 解析、总时限和取消。参见 [ethers 官方接口](https://docs.ethers.org/v6/api/utils/fetching/)。
- 本次锁定版本 HTTP 错误的头在 `error.response.headers`，不是 `error.info.response.headers`；info 保存 requestUrl、responseBody、responseStatus。
- eth_call 的封装结论成立；“eth_estimateGas 任何错误都如此”不精确，其先处理 INSUFFICIENT_FUNDS 和 NONCE_EXPIRED。
- 确定性的返回大小超限不应向同一端点反复发送原调用。应降低批量或选已验证兼容的端点；不使用宽泛 `/limit/`，不把所有 -32603 或带回滚数据的错误改成可重试。

### 限流证据边界

- 15:02 UTC 的额外有限检查为每链最多 5 个 POST，每个含 3 个 eth_chainId，总共 10 个小型 POST，无重试、链间冷却；全部 HTTP 200 成功，没有触发限流。未进行持续压测或耗尽日额度。
- 复查已有 v1.1.8 发布证据，两个 Tenderly CREATE2 探针曾收到 HTTP 429，JSON -32005 / rate limit exceeded。此为历史证据，不伪称本轮触发。
- [Tenderly 官方说明](https://docs.tenderly.co/node-rpc/overview#public-endpoint-limits)记载无密钥端点按 IP 每日 1 GB 响应数据，超额 HTTP 429 / -32005。一般批量单项错误可走 HTTP 200，不证明所有限流路径都如此。
- 观察到 X-TDLY-LIMIT:20，但未核实窗口及权重，**不解释为 20 QPS**。
- 客户端应防御性兼容 HTTP 429 和明确暂态的 JSON-RPC 限流错误；目前不能断言网关永远只用其中一种。

## 6. 严重度与后续改动估算

P2-i1 是用户可见的异常路径安全指令缺失翻译，按原报告的 P2 尺度合理。未发现翻译文本参与签名、nonce 或锁门禁判断，不能升级描述为已证实的交易安全绕过。修复应使用明确模板或结构化片段，钉住“请勿重发/清除”等语义，同时保留外部原始诊断。

以下仅为实现及相关验证的估算，不是本 PR 已做的修复，也不是承诺工期。

| 建议 | 预期改动与验证 | 估算 |
| --- | --- | --- |
| maxAttempts:2 | endpoint 一处配置；真实传输验证 1 秒/30 秒/无头、POST 数、成功、取消、超时；统一重试还需总预算及 Retry-After 辅助逻辑 | 仅限制次数约半天；统一逻辑约 1 天 |
| 原始 JSON 错误分类 | 约 30-80 行分类逻辑及表驱动；覆盖 -32005、暂态超时、大小超限、明确 revert、未知内部错误 | 半天至 1 天 |
| 安全提示与扫描 | 文案表、必要组句和语义断言；扫描使用 AST/明确展示入口/受审 allowlist，不一刀切禁止所有英文 | 1-2 天 |
| ethers vendor 块 | 约 5-15 行构建配置实验；检查双语冷启动、缓存切换、资源 404、180/220 KiB 两个门槛及请求数量 | 半天至 1 天 |

四项可分成独立变更，通常约 3-5 个工程日。分包不自动减少总下载和解析量；176.65 KiB 的余量值得提前测，但不保证下一功能必超限。请求级故障转移另需设计 deadline、取消、上下文和迟到结果处理，不包含在一行节流配置中。

## 7. 最初十项建议的取舍

| # | 复核意见 | 安全实施边界 |
| --- | --- | --- |
| 1 | 做请求级容错，不把等优先级当作已验证修复 | 有界、只读、已校验端点池；不无差别放行 -32603。 |
| 2 | 建议统一为一层重试 | 正确解析 Retry-After 秒/HTTP-date，限制并发、总预算；maxAttempts:2 仅缓解。 |
